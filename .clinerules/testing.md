# 测试规范

## TDD 工作流（执行 OpenSpec 变更时强制）

在执行 `/opsx-apply` 时，必须严格遵循以下顺序：

1. **写任何生产代码之前**，先读取当前变更目录下的 `specs/` 文件夹，理解每个场景（Scenario）的 Given / When / Then。
2. 针对规格中的每个场景，**先写一个失败的测试**。
3. 运行测试套件，**确认它失败的原因是正确的**——即因为“实现还不存在”，而不是因为拼写错误、导入错误或语法问题。
4. 确认失败原因正确后，才编写让测试通过的生产代码。
5. **禁止**在没有对应失败测试的情况下编写实现代码。

如果当前变更的 `tasks.md` 没有按“先测试、后实现”的顺序排列任务，**先重构 `tasks.md` 的排序**，再开始执行。

## 测试质量要求

- 测试必须包含**真实断言**，不能使用 `expect.fail("TDD 红阶段")`、`assert True`、空测试体等占位写法来“假装失败”。
- 每个测试应只验证一个行为，测试名称要能清楚表达“在什么条件下、期望什么结果”。
- 测试文件与被测代码放在对应的测试目录中，遵循项目已有的测试文件命名和目录约定。

## 红-绿-重构循环

对每一个任务单元：

1. **红**：写一个失败的测试，运行并确认失败。
2. **绿**：写最少的实现代码让测试通过，不提前添加未被测试覆盖的功能。
3. **重构**：在测试保持通过的前提下，清理代码结构和命名。

每完成一个任务单元，在 `tasks.md` 中勾选对应项，再进入下一个任务单元。

## 完成标准

一个任务只有同时满足以下条件才算完成：

- 对应测试已编写并运行
- 测试从失败转为通过（有明确的红-绿过程）
- 没有跳过或注释掉任何测试
- `tasks.md` 中该任务已勾选

如果无法为某个任务写出测试，必须向用户说明原因，而不是跳过测试直接写实现。
